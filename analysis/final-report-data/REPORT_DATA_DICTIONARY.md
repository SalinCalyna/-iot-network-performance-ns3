# Report Data Dictionary

Read-only reference for every metric used in `analysis/final-report-data/`. All definitions are drawn from the actual simulator source (`scratch/iot-network-v3-ext.cc` for V3/V4, `scratch/iot-network-bottleneck-probe.cc` for §10/retry/rate-sweep) and the existing approved analysis reports — nothing here is newly invented.

| Metric | Definition | Unit | Source dataset(s) | Aggregation | Seed range | Cross-protocol comparable? | Known caveat |
|---|---|---|---|---|---|---|---|
| **PDR** | `100 * PacketsReceived / PacketsSent` (FlowMonitor, gateway-bound flows only) | % | V3, V4, §10, Retry, Rate Sweep | mean/sd across seeds | 20-30 (V3/V4), 20-30 (§10), 20/25/30 (Retry, Rate Sweep) | Yes for OLSR/Static/V4. **Caution for AODV** — see below | **AODV FlowMonitor `PacketsSent` denominator artifact**: AODV's route discovery/repair/retransmission makes its transmitted-packet count scale with topology/route churn differently from OLSR/Static, so AODV PDR/PacketLoss are *indicative*, not an exact cross-protocol denominator (documented pre-existing limitation, confirmed unchanged by the integrity audit). |
| **ThroughputKbps** | Delivered bytes over the measurement window (`simTime - appStart`) × 8 / window, in kbps | kbps | V3, V4, §10, Retry, Rate Sweep | mean/sd | same as PDR | Yes | None beyond the general offered-load context (throughput is bounded by whatever rate was offered). |
| **AverageDelaySec / AverageJitterSec** | FlowMonitor per-flow delay/jitter sums divided by received-packet count | s | V3, V4, §10, Retry, Rate Sweep | mean/sd | same as PDR | Yes | None. |
| **PacketLoss / packet_loss_mean** | `PacketsSent - PacketsReceived` (V3/V4) or `txPkts - rxPkts` (§10-family) | packets | all | mean | same as PDR | Yes as a count; not decomposed into cause without the §10-family drop counters | A raw count says nothing about *why* packets were lost — see Residual Loss below. |
| **gw_airtime_busy_frac / ring1_airtime_busy_frac** | Fraction of `simTime` the gateway's (or ring-1 mean) WifiPhy spends in TX+RX+CCA_BUSY state | fraction [0,1] | §10, Retry, Rate Sweep only (not in V3/V4) | mean across seeds | 20-30 / 20,25,30 | Yes (same instrumentation for OLSR and Static) | The ~0.85-0.89 "near-saturation" figure is an **empirical reference observed in this topology**, not a universal theoretical CSMA/CA threshold. |
| **total_mac_queue_drops** | Count of `WifiMacQueue::DropBeforeEnqueue` + `DropAfterDequeue` events (queue-full drops), summed over all nodes | packets (count) | §10, Retry, Rate Sweep only | sum per run, meaned across seeds | 20-30 / 20,25,30 | Yes | Terminal, per-packet, mutually exclusive from `max_retry_drops` and IP-layer drops (verified from instrumentation source during the Static/N=50 diagnostic). |
| **total_phy_rx_drops** | Count of `WifiPhy::PhyRxDrop` trace events (failed receptions), summed over all nodes | events (count) | §10, Retry, Rate Sweep only | sum per run, meaned | 20-30 / 20,25,30 | Use with caution | **Does NOT directly equal permanent packet loss.** Includes frames that are retried and later succeed; established (M2) that PHY-event counts vastly exceed final application-level loss counts (100-200x in observed cells). Use only as a relative/directional signal, never as a loss-attribution numerator. |
| **total_max_retry_drops (MaxRetryDrops)** | Count of `WifiRemoteStationManager::MacTxFinalDataFailed` events — fires exactly once per MPDU finally dropped after exceeding the retry limit | packets (count) | Retry, Rate Sweep, Static/N=50 Diagnostic only (not in §10 or V3/V4) | sum per run, meaned | 20,25,30 | Yes | **Terminal retry-exhaustion counter** — distinct from `MacTxDataFailed` (fires on every failed attempt including later-successful retries). Confirmed real and measurable, but a secondary mechanism (M2): typically 1.5-18% of total loss, concentrated at outer hops, not gateway-localized. |
| **NO_ROUTE / ROUTE_ERROR / TTL / other (IP-layer drops)** | `Ipv4L3Protocol::Drop` trace, split by `DropReason` | packets (count) | §10, Retry, Rate Sweep, Diagnostic | sum per run | 20-30 / 20,25,30 | Yes | Negligible (<2% of loss) in every dataset that carries this instrumentation — routing failure is consistently ruled out as a material loss cause. |
| **RoutingOverheadPackets** | V3/V4: count of packets on AODV control ports (654/698) classified by the FlowMonitor five-tuple | packets (count) | V3, V4 only | sum per run | 20-30 | **No — protocol-scoped metric, not a general control-traffic count** | **V3's `RoutingOverheadPackets` reads exactly 0 for every OLSR row.** This is a metric-coverage limitation of the V3 script's classifier (appears AODV-port-specific) — it is **NOT** evidence that OLSR generates zero HELLO/TC control traffic. Do not state or imply OLSR has no overhead based on this column. |
| **AverageHopCount** | Protocol-dependent hop-count approximation: Static uses exact route information; AODV/OLSR use an implemented approximation (`HopCountMethod` column, e.g. `approx_timesForwarded`) | hops | V3, V4 | mean per run | 20-30 | Caution — methodology differs by protocol | Direct AODV/OLSR vs. Static hop-count comparisons should note the differing measurement method (pre-existing, documented limitation, preserved unchanged). |
| **UnreachableSensors** | Count of sensor nodes with no route to the gateway at simulation end | count | V3, V4, §10-family (as `unreachableSensors`) | mean per run | 20-30 / 20,25,30 | Yes | Nonzero mainly at low N (sparse topology, a placement/geometry effect), zero at N>=50 in every dataset checked. |
| **Residual Loss / residual_pct** | `TotalLoss - (MacQueueDrops + MaxRetryDrops + NO_ROUTE + TTL + ROUTE_ERROR + other)`, as a % of TotalLoss | % | Static/N=50 Diagnostic (12 runs) | per-run | 20,25,30 | N/A (single-protocol diagnostic) | **Do not claim a specific physical cause for this residual.** It is a quantified gap (64.7-99.6% of loss, typically >=92%), not an identified mechanism. The largest circumstantial (not confirmatory) signal is PHY RX-drop volume, per the caveat above. |
| **PathChanges** | V4: count of *within-run* route-tree changes (dynamic re-routing events during a single simulation) | count | V4-matched, V4-sensitivity, V4-Tier1 | per run | 20-30 | N/A (V4-specific) | **Always 0 across all 957 V4 rows in every dataset** — by design, V4 installs one fixed route tree per run and never re-routes mid-run. This is NOT evidence V4 fails to activate; activation is measured instead by "route-tree diff from Static" (fraction of seeds whose resulting tree differs from Static's shortest-path tree), which does show activation (up to 100% of seeds at the strongest tested config). |
| **route_change_pct / ACTIVATED (V4 Tier-1)** | % of seeds where V4's resulting route tree differs from Static's, and a boolean pre-registered >=30% activation threshold | % / boolean | V4-Tier1 (66 rows) | per-config, across 11 seeds | 20-30 | N/A (V4-specific) | The correct, validated way to demonstrate "V4 activates" — do not substitute `PathChanges` for this. |

## Notes on pooling

- V3/V4 "pooled" statistics in `v3_core_results.csv` and `v4_results.csv` average over **traffic level × mobility mode** at fixed protocol × node count, unless a row explicitly states a single traffic/mobility condition. Always check the `traffic`/`mobility` columns before quoting a pooled figure as if it were a single-condition result.
- §10/Retry/Rate-Sweep files are never pooled across node count or traffic — every row is a single (protocol, N, traffic-or-rate) cell, meaned only across seeds.
